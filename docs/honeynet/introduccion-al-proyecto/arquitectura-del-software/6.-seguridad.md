# 6. Seguridad

## Firewall (UFW) y mínimo privilegio

Cada servidor deniega todo el tráfico entrante por defecto y solo abre lo que necesita. La administración por SSH solo se acepta desde la VLAN de Gestión.

| Servidor      | Entrada permitida | Origen                          |
| ------------- | ----------------- | ------------------------------- |
| `ct-web`      | 80/tcp y 443/tcp  | Cualquiera                      |
| `ct-web`      | 22/tcp            | VLAN 30 (10.0.30.0/24)          |
| `ct-db`       | 3306/tcp          | **Solo** `ct-web` (10.0.60.10)  |
| `ct-db`       | 22/tcp            | VLAN 30                         |
| `ct-dns-dhcp` | 53/tcp y 53/udp   | VLAN 20, 40 y 60                |
| `ct-dns-dhcp` | 67/udp            | pfSense, como relay (10.0.20.1) |
| `ct-dns-dhcp` | 22/tcp            | VLAN 30                         |
| `ct-backup`   | 22/tcp            | VLAN 30                         |

Ejemplo en `ct-db`, donde la base de datos solo acepta conexiones del servidor web y se bloquea el resto:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 10.0.60.10 to any port 3306 proto tcp
sudo ufw allow from 10.0.30.0/24 to any port 22 proto tcp
sudo ufw enable
sudo ufw status verbose
```

Además, MariaDB escucha solo en su IP (`bind-address = 10.0.20.11`), de modo que el cortafuegos no es la única barrera. La base de datos solo guarda el contenido de la web, así que la DMZ no necesita conectarse a ella.

## Reglas de pfSense entre VLANs

UFW protege cada servidor y pfSense decide qué VLAN puede hablar con cuál. Todo lo que no esté en esta tabla queda bloqueado:

| Origen                                                    | Destino                       | Puerto                             | Motivo                     |
| --------------------------------------------------------- | ----------------------------- | ---------------------------------- | -------------------------- |
| `ct-web` (VLAN 60)                                        | `ct-db` (10.0.20.11)          | 3306/tcp                           | Consultas de la web        |
| `ct-web`                                                  | `ct-dns-dhcp` (10.0.20.10)    | 53/tcp y udp                       | Resolver nombres           |
| `ct-web`                                                  | VM SIEM, Grafana (10.0.30.10) | 3000/tcp                           | Proxy de `/grafana/`       |
| Honeypots, `ct-web`, `ct-db`, `ct-dns-dhcp` y `ct-backup` | VM SIEM, Wazuh (10.0.30.10)   | 1514/tcp y 1515/tcp                | Agentes de logs            |
| VLAN 40                                                   | `ct-web`                      | 80/tcp y 443/tcp                   | Usar la web                |
| VLAN 40                                                   | `ct-dns-dhcp`                 | 53 y relay DHCP (67/udp)           | Nombres y direcciones IP   |
| VLAN 50 (Kali)                                            | `ct-web` y honeypots          | 80 y 443; puertos de los honeypots | Pruebas de ataque          |
| VLAN 30 (Gestión)                                         | Todas las VLANs               | SSH y administración               | Administrar el laboratorio |

## Gráficos y logs de Grafana dentro de la web

Los logs y los gráficos de `/admin` son paneles de Grafana. Para que el administrador los vea sin abrir la VLAN de Gestión a los usuarios, nginx hace de proxy:

1.  **`/admin` y `/grafana/` solo desde la red interna.** En nginx se limitan por IP, de modo que aunque la web pública se vea desde fuera, la zona de administración no:

    ```nginx
    location /grafana/ {
        allow 10.0.30.0/24;   # Gestión (incluye NetBird)
        allow 10.0.40.0/24;   # VLAN de usuarios
        deny all;
        proxy_pass http://10.0.30.10:3000/;
    }
    ```
2.  **Grafana solo con lo necesario.** Se activa que se pueda incrustar y que sirva bajo `/grafana/`. Como solo se llega desde `ct-web`, el acceso anónimo se limita al rol de solo lectura (Viewer):

    ```ini
    [server]
    root_url = %(protocol)s://%(domain)s/grafana/
    serve_from_sub_path = true
    [security]
    allow_embedding = true
    [auth.anonymous]
    enabled = true
    org_role = Viewer
    ```
3. **Comprobar la configuración en la documentación de la versión instalada**, porque estos parámetros pueden variar entre versiones.
4. **El login de la web es la puerta.** Sin sesión de administrador no se muestra la pestaña de gráficos, y la protección de red es una segunda barrera.
5. **No se muestran logs en bruto en páginas propias.** Los logs de los honeypots contienen texto que escribe el atacante (usuarios, comandos), así que se ven solo a través de los paneles de Grafana, que escapan el contenido.

## Conexión segura: SSH con claves

El acceso a los servidores se hace con un par de claves en lugar de contraseña:

1. Se genera un par de claves de tipo ed25519 en el equipo del administrador.
2. Se copia la clave pública a cada servidor.
3. En el archivo de configuración del servicio SSH se desactiva el acceso con contraseña y el acceso directo del usuario root.
4. Se reinicia el servicio.

{% hint style="warning" %}
Comprueba que entras con la clave en una segunda terminal antes de cerrar la sesión actual, para no quedarte sin acceso.
{% endhint %}

## Prevención de inyecciones SQL

Nunca se concatena la entrada del usuario en una consulta. Se usan **consultas preparadas con PDO** que llaman a **procedimientos almacenados**, así los datos viajan siempre separados de la consulta:

```php
$pdo = new PDO($dsn, $usuario, $clave, [
    PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_EMULATE_PREPARES => false,
]);

$stmt = $pdo->prepare(
    'CALL sp_registrar_mensaje(:nombre, :apellidos, :telefono, :mensaje, :id_plan)'
);
$stmt->execute([
    ':nombre'    => $_POST['nombre'],
    ':apellidos' => $_POST['apellidos'],
    ':telefono'  => $_POST['telefono'],
    ':mensaje'   => $_POST['mensaje'],
    ':id_plan'   => $_POST['id_plan'] ?: null,
]);
```

Otras medidas del backend:

* Validar longitud y formato de cada campo antes de guardar, en línea con los límites de la base de datos (que además los comprueba con restricciones y triggers).
* Escapar con `htmlspecialchars()` todo lo que se muestre en pantalla, para evitar XSS.
* Guardar las contraseñas con `password_hash()` y comprobarlas con `password_verify()`. La base de datos rechaza cualquier contraseña que no llegue ya cifrada.

## Credenciales ocultas

Las credenciales no van en el código ni en el repositorio. Se guardan en un archivo `.env` fuera de la carpeta pública, con permisos 640 (propietario root, grupo www-data) y excluido de Git mediante `.gitignore`. Además, nginx bloquea el acceso a los archivos ocultos.

Contenido de ejemplo del `.env`, con una credencial para la zona pública y otra para el panel de administración:

```
DB_HOST=10.0.20.11
DB_NAME=honeypot_web
DB_USER=web_app
DB_PASS=contraseña_larga_y_aleatoria
DB_ADMIN_USER=web_admin
DB_ADMIN_PASS=otra_contraseña_larga_y_aleatoria
```

## Usuarios de base de datos con mínimos privilegios

La web no se conecta como administrador de la base de datos. Usa **dos usuarios**, que solo pueden **ejecutar procedimientos** (no leen ni escriben las tablas directamente) y solo desde `ct-web`:

| Usuario     | Para qué                | Procedimientos que puede ejecutar                                                                                            |
| ----------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `web_app`   | Zona pública            | `sp_listar_planes`, `sp_listar_sectores`, `sp_registrar_mensaje`, `sp_obtener_usuario_login` y `sp_registrar_intento_acceso` |
| `web_admin` | Panel de administración | Gestión de mensajes, planes, sectores y administradores, e informes                                                          |

```sql
DROP USER IF EXISTS 'web_app'@'10.0.60.10';
CREATE USER 'web_app'@'10.0.60.10' IDENTIFIED BY 'contraseña_larga_y_aleatoria';
GRANT EXECUTE ON PROCEDURE honeypot_web.sp_listar_planes TO 'web_app'@'10.0.60.10';
GRANT EXECUTE ON PROCEDURE honeypot_web.sp_registrar_mensaje TO 'web_app'@'10.0.60.10';
-- ... y el resto de procedimientos de la zona pública
FLUSH PRIVILEGES;
```

Así, aunque alguien explotara un fallo de la parte pública de la web, no podría ejecutar las operaciones de administración. La lista completa de permisos está en el script `honeypot_web.sql` (ver [Diagrama de la base de datos](3.-diagrama-de-la-base-de-datos.md)).

## Protecciones dentro de la base de datos

* **Bloqueo de cuentas:** cinco intentos fallidos en 15 minutos bloquean la cuenta del administrador durante 15 minutos (un trigger lo aplica y `sp_obtener_usuario_login` rechaza la cuenta bloqueada).
* **Contraseñas siempre cifradas:** un trigger impide guardar una contraseña que no tenga formato bcrypt o argon2.
* **Anti-spam:** el formulario de contacto acepta como máximo tres mensajes por teléfono cada diez minutos.
* **Último administrador protegido:** no se puede borrar ni desactivar.
* **Auditoría:** las altas, cambios y bajas de usuarios y los cambios en planes y sectores quedan registrados, junto con el historial de precios.

## Resumen de medidas

| Requisito                             | Medida aplicada                                                                                                                  |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Cortafuegos con mínimo privilegio     | UFW con entrada denegada por defecto; la base de datos solo acepta al servidor web. pfSense solo permite los flujos de la tabla. |
| Acceso seguro al servidor             | SSH solo con claves, sin contraseña ni root, y solo desde la VLAN de Gestión.                                                    |
| Prevención de inyecciones SQL         | Consultas preparadas con PDO, procedimientos almacenados y validación de los campos.                                             |
| Credenciales ocultas                  | `.env` fuera de la carpeta pública, con permisos 640 y excluido de Git.                                                          |
| Mínimo privilegio en la base de datos | Dos usuarios (`web_app` y `web_admin`) que solo ejecutan procedimientos y solo desde `ct-web`.                                   |
| Protección del login                  | Registro de intentos, bloqueo temporal tras cinco fallos y contraseñas cifradas con bcrypt o argon2.                             |
| Zona de administración protegida      | `/admin` y `/grafana/` limitados por IP, login de administrador y Grafana solo con rol de lectura.                               |
