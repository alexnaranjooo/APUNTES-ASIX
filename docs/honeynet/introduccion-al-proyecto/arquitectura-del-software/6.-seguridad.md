# 6. Seguridad

## Firewall (UFW) y mínimo privilegio

Cada servidor deniega todo el tráfico entrante por defecto y solo abre lo que necesita. La administración por SSH solo se acepta desde la VLAN de Gestión.

| Servidor      | Entrada permitida | Origen                             |
| ------------- | ----------------- | ---------------------------------- |
| `ct-web`      | 80/tcp y 443/tcp  | Cualquiera                         |
| `ct-web`      | 22/tcp            | VLAN 30 (192.168.30.0/24)          |
| `ct-db`       | 3306/tcp          | **Solo** `ct-web` (192.168.60.10)  |
| `ct-db`       | 22/tcp            | VLAN 30                            |
| `ct-dns-dhcp` | 53/tcp y 53/udp   | VLAN 20, 40 y 60                   |
| `ct-dns-dhcp` | 67/udp            | pfSense, como relay (192.168.20.1) |
| `ct-dns-dhcp` | 22/tcp            | VLAN 30                            |
| `ct-backup`   | 22/tcp            | VLAN 30                            |

Ejemplo en `ct-db`, donde la base de datos solo acepta conexiones del servidor web y se bloquea el resto:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.60.10 to any port 3306 proto tcp
sudo ufw allow from 192.168.30.0/24 to any port 22 proto tcp
sudo ufw enable
sudo ufw status verbose
```

Además, MariaDB escucha solo en su IP (`bind-address = 192.168.20.11`), de modo que el cortafuegos no es la única barrera. Si se usa el plugin de MySQL de Cowrie, se añade una excepción documentada para la VM de los honeypots, solo al puerto 3306.

## Conexión segura: SSH con claves

El acceso a los servidores se hace con un par de claves en lugar de contraseña:

1. Se genera un par de claves de tipo ed25519 en el equipo del administrador.
2. Se copia la clave pública a cada servidor.
3. En el archivo de configuración del servicio SSH se desactiva el acceso con contraseña y el acceso directo del usuario root.
4. Se reinicia el servicio.

{% hint style="warning" %}
Comprueba que entras con la clave en una segunda terminal antes de cerrar la sesión actual, para no quedarte sin acceso.
{% endhint %}

## Prevención de inyecciones SQL

Nunca se concatena la entrada del usuario en una consulta. Se usan **consultas preparadas con PDO**, que separan la consulta de los datos:

```php
$pdo = new PDO($dsn, $usuario, $clave, [
    PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
    PDO::ATTR_EMULATE_PREPARES => false,
]);

$stmt = $pdo->prepare(
    'INSERT INTO mensajes_contacto (nombre, apellidos, telefono, mensaje)
     VALUES (:nombre, :apellidos, :telefono, :mensaje)'
);
$stmt->execute([
    ':nombre'    => $_POST['nombre'],
    ':apellidos' => $_POST['apellidos'],
    ':telefono'  => $_POST['telefono'],
    ':mensaje'   => $_POST['mensaje'],
]);
```

Otras medidas del backend:

* Validar longitud y formato de cada campo antes de guardar, en línea con los límites de la base de datos.
* Escapar con `htmlspecialchars()` todo lo que se muestre en pantalla, para evitar XSS.
* Guardar las contraseñas con `password_hash()` y comprobarlas con `password_verify()`.

## Credenciales ocultas

Las credenciales no van en el código ni en el repositorio. Se guardan en un archivo `.env` fuera de la carpeta pública, con permisos 640 (propietario root, grupo www-data) y excluido de Git mediante `.gitignore`. Además, nginx bloquea el acceso a los archivos ocultos.

Contenido de ejemplo del `.env`:

```
DB_HOST=192.168.20.11
DB_NAME=honeypot_web
DB_USER=web_app
DB_PASS=contraseña_larga_y_aleatoria
```

## Usuario de base de datos con mínimos privilegios

La web no se conecta como administrador de la base de datos, sino con un usuario que solo puede hacer lo imprescindible y solo desde `ct-web`:

```sql
CREATE USER 'web_app'@'192.168.60.10' IDENTIFIED BY 'contraseña_larga_y_aleatoria';
GRANT SELECT ON honeypot_web.planes TO 'web_app'@'192.168.60.10';
GRANT SELECT ON honeypot_web.caracteristicas TO 'web_app'@'192.168.60.10';
GRANT SELECT ON honeypot_web.plan_caracteristica TO 'web_app'@'192.168.60.10';
GRANT SELECT ON honeypot_web.sectores TO 'web_app'@'192.168.60.10';
GRANT SELECT ON honeypot_web.ataques TO 'web_app'@'192.168.60.10';
GRANT SELECT ON honeypot_web.usuarios TO 'web_app'@'192.168.60.10';
GRANT SELECT ON honeypot_web.roles TO 'web_app'@'192.168.60.10';
GRANT INSERT ON honeypot_web.mensajes_contacto TO 'web_app'@'192.168.60.10';
FLUSH PRIVILEGES;
```

## Resumen de medidas

| Requisito                             | Medida aplicada                                                                     |
| ------------------------------------- | ----------------------------------------------------------------------------------- |
| Cortafuegos con mínimo privilegio     | UFW con entrada denegada por defecto; la base de datos solo acepta al servidor web. |
| Acceso seguro al servidor             | SSH solo con claves, sin contraseña ni root, y solo desde la VLAN de Gestión.       |
| Prevención de inyecciones SQL         | Consultas preparadas con PDO y validación de los campos.                            |
| Credenciales ocultas                  | `.env` fuera de la carpeta pública, con permisos 640 y excluido de Git.             |
| Mínimo privilegio en la base de datos | Usuario `web_app` con permisos mínimos y solo desde `ct-web`.                       |
